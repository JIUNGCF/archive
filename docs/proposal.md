# Archive 사이트 구축 제안 (JIU-5)

> 상태: **제안 / Board 결정 대기**. 이 문서는 방향을 확정하지 않는다. 후보를 제시하고 멈춘다.
> 아키텍처·기술 스택 확정은 Board 승인 후 별도 이슈에서 진행한다.

## 1. 목표 이해

"나만의 Archive 페이지". 연구 / 개발 / 경험 / 독서 4개 카테고리의 글을 모아 둔다.

- **홈**: 첫 화면에서 콘텐츠가 그리드로 한눈에 보인다.
- **상세**: 항목을 누르면 들어가서 사진·동영상과 본문을 본다.
- **작성/편집**: 블로그처럼 사진·동영상을 올리고 글을 쓰고 수정한다.

첨부된 참고 이미지 2장(TM RSI SGM Research Archive, Schweizer Designpreis) 분석:

- **참고1 (홈)**: 어두운 배경, 타이포그래피 중심. 상단 가로 내비게이션(카테고리), 우측 검색창 + "Updates" 사이드바, 본문은 썸네일 **그리드**. → 홈/목록 화면의 레퍼런스.
- **참고2 (상세)**: 좌측 대표 미디어 1개, 우측에 **구조화된 메타데이터**(저자/제작/출처 등) + 본문 텍스트, 사이드바 내비게이션. → 상세 화면의 레퍼런스.

→ 방향성: **미니멀 · 타이포 중심 · 그리드 목록 → 메타데이터 상세**의 에디토리얼 아카이브.

## 2. 정보 구조 (IA)

```
홈 (/)  ─ 카테고리 필터: 연구 · 개발 · 경험 · 독서 / 전체
  └─ 카드 그리드 (썸네일 + 제목 + 날짜 + 카테고리)
        └─ 상세 (/{category}/{slug})
              ├─ 대표 미디어 (이미지 / 동영상)
              ├─ 메타데이터 (날짜, 태그, 출처 등)
              └─ 본문 (텍스트 + 인라인 이미지/영상)
  └─ 작성/편집 (/write, /{category}/{slug}/edit)  ※ 본인만
```

## 3. 콘텐츠 모델 (글 1개 스키마 초안)

| 필드 | 타입 | 설명 |
|---|---|---|
| id / slug | string | URL 식별자 |
| category | enum | research / dev / experience / reading |
| title | string | 제목 |
| date | date | 작성·발행일 |
| cover | media | 그리드 썸네일 |
| tags | string[] | 필터·검색용 |
| body | rich text | 본문 (이미지·영상 임베드 포함) |
| media[] | media[] | 첨부 사진·동영상 |
| status | enum | draft / published |

이 스키마는 정적/동적 어느 방식이든 공통으로 쓸 수 있다.

## 4. Board가 정해야 할 핵심 결정 (여기서 멈춘다)

### 결정 A — 아키텍처 방식 (가장 중요)

| 후보 | 개요 | 장점 | 단점 |
|---|---|---|---|
| **A1. 정적 사이트 (SSG)** | 글을 Markdown 파일로 두고 Next.js/Astro 등으로 빌드 | 무료 호스팅(GitHub Pages 등), 빠름·단순, DB 불필요 | 웹에서 글쓰기 UI 없음(파일 직접 편집), 동영상은 외부 링크 권장 |
| **A2. 동적 앱 (DB+백엔드+인증)** | 브라우저에서 로그인→작성/수정, DB 저장 | 요구사항의 "블로그처럼 작성·수정" 완전 충족 | 서버·DB·인증 필요, 운영 비용·복잡도↑ |
| **A3. 헤드리스 CMS / SaaS 백엔드** | Notion·Sanity·Supabase 등을 데이터 소스로, 프런트만 구축 | 작성 UI를 직접 안 만들어도 됨, 미디어 업로드 내장 | 외부 서비스 의존, 무료 한도·잠금 고려 |

> 참고: 요구사항의 "웹에서 사진·동영상 올리고 글 쓰고 수정" 을 그대로 만족시키려면 A2 또는 A3이 자연스럽다. A1은 가장 단순하지만 "웹 작성 UI"는 포기(또는 별도 관리자 도구 필요)한다.

### 결정 B — 미디어(사진/동영상) 저장
- B1. 저장소(리포)에 직접 커밋 — 간단하지만 동영상 용량 부담(권장 X)
- B2. 오브젝트 스토리지(S3/Cloudflare R2/Supabase Storage 등)
- B3. 동영상은 외부(YouTube/Vimeo) 임베드 + 이미지는 스토리지

### 결정 C — 편집(작성/수정) UX
- C1. 웹 에디터(로그인 후 브라우저에서) — 동적 방식 필요
- C2. 로컬에서 Markdown 작성 후 커밋/배포 — 정적 방식

### 결정 D — 호스팅
- 정적: GitHub Pages / Cloudflare Pages / Vercel(무료)
- 동적: Vercel + 관리형 DB / Supabase / 자체 서버

## 5. 추천안 (참고용, 확정 아님)

균형점으로 **A3(헤드리스/SaaS 백엔드) + B3(영상 임베드·이미지 스토리지) + C1(웹 에디터)** 조합을 우선 후보로 제안한다.
근거: "웹에서 작성·수정 + 미디어 업로드" 요구를 충족하면서, 작성 UI/인증/스토리지를 직접 구현하지 않아 초기 구축 규모가 작다.
단, 외부 서비스 의존을 피하고 싶다면 **A2 자체 구축**, 최소 비용·최대 단순이면 **A1 정적**이 대안이다.

## 6. 단계별 로드맵 (방향 확정 후)

1. 스택 확정(결정 A~D) → 리포 초기화 · 기본 레이아웃
2. 홈 그리드 + 카테고리 필터 (참고1 레이아웃)
3. 상세 페이지 (참고2 레이아웃) + 미디어 렌더
4. 작성/수정 + 미디어 업로드 (선택한 방식대로)
5. 검색 · Updates 사이드바 · 마감(반응형/접근성)

2. **결정 B~D** — 미디어 저장 / 편집 UX / 호스팅 선호가 있는지, 아니면 A 선택에 맞춰 위임할지?

## 8. Board 1차 답변 반영 & 결정 B~D 재설명

> Board 결정 (2026-08-13): **결정 A = A3 (작성 UI 내장 서비스)**, **범위 = 처음부터 작성·수정 기능 포함(full)**.
> 결정 B~D는 "이해하지 못했으니 다시 설명해 달라"는 요청 → 아래에서 쉬운 말로 재설명하고 확정안을 제시한다.

### 8.1 먼저 큰 그림

**B, C, D는 A3(작성 UI 내장 서비스)를 고르면 대부분 자동으로 함께 정해집니다.**
따라서 어려운 결정 3개가 따로 있는 게 아니라, "어떤 서비스를 쓸지" 하나만 고르면 나머지가 딸려옵니다.
(A3이 매력적인 이유가 바로 이것 — 저장·로그인·업로드를 직접 안 만들어도 됨.)

### 8.2 각 결정의 뜻 (일상 비유)

- **결정 B — 미디어 저장: "사진·동영상 파일을 어디에 둘까?"**
  글 안에 들어가는 사진·동영상 **파일 자체를 보관하는 창고**를 정하는 일.
  - 사진: 서비스가 주는 저장소에 그대로 업로드해 보관.
  - 동영상: 용량이 매우 큼(사진의 수십~수백 배). 직접 보관하면 느리고 비쌈. → **긴 영상은 유튜브/비메오에 올리고 "링크만 가져와 삽입"**을 권장. 짧은 영상은 저장소에 직접 둬도 됨.

- **결정 C — 편집: "글을 어떻게 쓰고 고칠까?"**
  요청하신 "블로그처럼 웹에서 작성·수정" = 사이트에 **본인만 로그인**한 뒤, 브라우저 화면에서 글쓰기·사진 올리기·수정을 하는 방식(프로그램 설치 없이 웹에서).

- **결정 D — 호스팅: "이 웹사이트가 실제로 돌아가는 곳"**
  사이트를 인터넷에 띄워 두는 서버. 개인 규모는 **무료 등급**으로 충분.

### 8.3 추천 확정안 (A3 + full)

| 항목 | 추천 | 쉬운 설명 | 비용 |
|---|---|---|---|
| 글 데이터·로그인·사진 저장 | **Supabase** | 글 저장 + 본인 로그인 + 사진 업로드를 한 곳에서 제공 | 무료 등급 |
| 동영상 | **유튜브/비메오 링크 임베드** (짧은 건 Supabase 직접) | 긴 영상은 링크만 붙이면 됨 | 무료 |
| 사이트(프런트) | **Next.js + Vercel** | 홈 그리드·상세·글쓰기 화면 구현·배포 | Vercel 무료 |

→ 이렇게 하면 "웹에서 로그인해 사진·동영상 올리고 글 쓰고 수정" 요구가 처음부터 전부 충족되고, 서버·DB를 직접 운영하지 않아 개인이 관리하기 쉽습니다.

**대안**: 글쓰기 화면조차 만들기 싫다면 **Notion / Sanity**를 백엔드로 쓰면 그 서비스 앱에서 글을 쓰고 사이트는 보여주기만 합니다(웹 에디터를 아예 안 만듦). 대신 디자인 자유도·동영상 처리에 제약이 있습니다.

### 8.4 다음 단계

이 확정안(**A3: Supabase + Next.js/Vercel + 영상 임베드**)에 **동의**하시면, 확정된 스택으로
① 리포 초기화·기본 레이아웃 → ② 홈 그리드 → ③ 상세 → ④ 로그인·작성/수정·미디어 업로드
순서로 전체 작업을 진행하겠습니다. 동의 전까지는 착수하지 않습니다.
